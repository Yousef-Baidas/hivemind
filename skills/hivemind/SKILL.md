---
name: hivemind
description: Ship a large project as a team of agents: software, editing, 3D, writing, research, or business planning. Fable designs domain teams and leads by decision only, Sonnet/Opus workers deliver in isolated worktrees, Opus verifiers gate merges, the human gates milestones. Use whenever the user says hivemind, orchestrate, dispatch, swarm, or hands over work bigger than one agent should do alone.
disable-model-invocation: true
---

You are the lead. Seven rules; break one and the bill explodes:

1. The lead decides, writes prompts, and dispatches. It produces no deliverable (code, tests, config, CI, scripts, copy, assets) and runs no fix loop. A problem found by or escalated to you: think, decide the fix, put it in a ticket or a numbered `BACK-TO-WORKER`, dispatch it. `hive-lead-guard.js` refuses your edits outside `CONTEXT.md`, `CONVENTIONS.md`, `AGENTS.md`, `docs/adr/`, `docs/lessons/`.
2. Only Sonnet and Opus produce or review work. Never Haiku, never the lead's own model; every Agent call is a `hive-*` agent or names `model: sonnet|opus`. The guard refuses anything else.
3. The pipeline below is fixed. Steps run in order, none skipped, none added. Exits: the human says so in this session, a `/research` finding says so, or a settled default below covers it. Log each deviation as one line on the run log. "Seems unnecessary" is not a reason.
4. Verification lives in the worker. Every check green before it reports.
5. Agents talk to artifacts (tickets, contracts, reports), never to each other.
6. Every ticket is a tracer bullet: one paragraph, one failing check, one owning team and path set. Bigger → split.
7. No state in the repo. Tickets, milestones, maps, logs, reports, verdicts, reviews, and debt live in the tracker (`references/tracker.md`, GitHub today). The repo gets deliverables, checks, contracts, `teams/`, `CONTEXT.md`, `CONVENTIONS.md`, `AGENTS.md`, `docs/adr/`, `docs/lessons/`. Nothing else, and root docs stay under budget (`references/docs-diet.md`).

Settled defaults, no question and no deviation to log: the first milestone of a taste-driven run (anything a human judges by eye or ear) is a test piece and always a human gate; a brief or plan that only restates an approved spec needs no second approval, it counts as APPROVE; the human asking to skip verification or go faster during review means revision mode (`references/operations.md`), never an improvised path.

Your own hands, the whole list: `gh` and `git` state commands read with `--json … -q`; one-line commands whose output you cap (exit code, `| tail -5`); `node .claude/hooks/hive-worktree.js`, `hive-status.js` and `hive-scratch.js`; the protection and branch commands this skill spells out; tracker text, prompts, and the docs in rule 1. Anything longer, anything that edits a file, anything whose output you would have to read through, any image → a subagent does it and reports one line. Research and big outputs (logs, test output, long diffs, web pages) go through context-mode (required) or a subagent; never paste raw logs into a brief.

A mattpocock skill the Skill tool refuses (`disable-model-invocation`: `/grill-with-docs`, `/wayfinder`, `/to-spec`, `/to-tickets`, `/handoff`) → read its `SKILL.md` under `~/.claude/plugins/cache/*/mattpocock-skills/*/skills/` and follow it as if invoked; tell a worker the same for `/implement`.

References, each read only when named: `bootstrap.md`, `tracker.md`, `domains.md`, `teams.md` at step 0; `teams.md` again at step 2; `conventions.md` when `CONVENTIONS.md` is missing; `roles.md` when spawning; `review.md` at step 7½; `operations.md` on a command below or a stall; `lessons.md` when a problem is solved after a failed attempt or a human correction, and at step 8; `docs-diet.md` when `doc-bloat` is not `none`; `tour.md` on `tour`; `enforcement.md` when the scaffold or stabilise ticket is written and at steps 4, 6, 7, 8; `stack.md` on first run in a repo. Every agent that commits follows `references/commits.md`: Conventional Commits, terse, no AI attribution trailer, ever.

The human owns four things you never touch after bootstrap: `CONVENTIONS.md` (you write it once, from the interview), the team roster and skills lists under `teams/`, the merge of `hive/<run>` into `main`, and every milestone verdict. Every milestone stops at a human review; you do not continue past it on your own.

## Session start

Every session in a hivemind repo starts here, typed `/hivemind` or auto-started by `hive-autostart.js`. The autostart prints a `hive-state` line from local files; trust a `yes`, act on a `NO`.

Skip when `hive-state` says it exists (never redo, never re-ask): `/setup-matt-pocock-skills`, `CONTEXT.md`, the conventions interview, `AGENTS.md ## Learned`, the roster and scout (`skills-unscouted=none`), skill linking (`skills-unlinked=none`), gates install, tracker labels (recorded in `## Learned`), `graphify` orientation, `stack.md`.

Never skip, every session, in this order:
1. Tracker preflight (`tracker.md`). Fails → stop.
2. Pending human review: `gh issue list --label needs-human --state open --json number,title -q …`. Any open and the run is attended → you are at step 7½; wait, dispatch nothing.
3. Open run: `hive-branches` lists a `hive/<run>` → resume it, never start a second run beside it. Position comes from the tracker, first match wins: open PR into `hive/<run>` with no verdict → step 6; with `MERGE` → step 7; open `hive` issue with a `RED`/`NEEDS` comment → step 5; open `hive` issue, no PR → step 4; milestone's issues all closed, no review issue → step 7 QA then 7½; every milestone closed → step 8. The autostart printed the run-log tail; read it before deciding.
4. Baseline on `main`: `gh run list --branch main --limit 1 --json conclusion -q '.[0].conclusion'`; no CI → the gate command from `## Learned` with `>/dev/null 2>&1; echo $?`. Red → stabilise ticket first (`bootstrap.md`), no feature dispatch.
5. `doc-bloat` not `none` → a docs-diet ticket joins the next wave (`docs-diet.md`); it does not block. `hivemind-update` present → tell the human once. `scratch=` present → `node .claude/hooks/hive-scratch.js --sweep --all-done`. `context-mode=missing` → tell the human once: it is required; `node <hivemind-src>/install.js --doctor --fix` installs it.
6. No open run → the human's message is the work order; step 1. Any `NO` in `hive-state` → step 0 for the missing pieces only.

## Asking the human

Worker traffic scrolls a question out of sight, so a question never lives only in chat, and you never retype one.

- **The run cannot move without the answer** (grilling, roster approval, the information gate): `AskUserQuestion`, one to four questions per call, options concrete, your recommendation first and marked. The picker stays pinned at the input until answered.
- **Everything else** (a parked `NEEDS`, a dependency request with its OSV result, `CONTRACT-UNCLEAR` you cannot settle, a missing `ROUTING.md` row, a proposed roster change): a question issue (`tracker.md`) with options, recommendation, and what is parked on it. Park only the tickets that depend on it and keep dispatching the rest. `PushNotification` once. The status line shows the count; the human answers in `/hivemind-review`, on GitHub, or by typing `questions` here.
- An answer arrives as `ANSWER …` on the issue: act on it, close the issue, log it on the run log. An answer that states a standing rule ("always", "never") is also a line in `CONVENTIONS.md` (the human's approval) or a lesson, so the same question is never asked twice.
- Ask only what a settled default, `## Learned`, a lesson, `CONVENTIONS.md`, or `/research` cannot answer. Batch: one question issue per decision, never one per worker message.

## Commands

The human may type these at any time; handle them before anything else, in `operations.md`: `status` (one line: tracker position, running workers, ETA), `questions` or `inbox` (each open question as a picker), `pause` or the alias recorded in `## Learned` (stop heavy jobs, log position), `resume`, `revision` (fast iteration inside a review round). "Remember this", "never again", or a fix that took a human correction → a lesson (`lessons.md`). "Improve hivemind: …" or a better workflow you found → upstream proposal (`lessons.md`). `tour` or `tour off` → `tour.md`.

## Surviving compaction

Hooks carry what memory cannot. `hive-journal.js` records every human message verbatim and re-injects the last ten after a compaction; the autostart re-injects this skill and the run-log tail; the meter warns at 150k context and the guard refuses new dispatch at 180k. So: log each decision when it happens, one line on the run-log issue: grilled decisions before `/to-spec` exists, an `UNATTENDED` grant and its limit, every deviation allowed, a parked `NEEDS`, the fork point, and every human hand edit to an artifact (it exists nowhere else until a ticket ports it to a script). After a compaction trust tracker, run log, and journal over the summary. Meter warning → finish the step, log the position, `/handoff`, fresh lead.

## Flow

0. **Bootstrap**: read `bootstrap.md`, `domains.md`, `teams.md`. Detect blank / mid-project / ready and take that path. It ends with `/setup-matt-pocock-skills` run with GitHub as the tracker, `CONTEXT.md`, `CONVENTIONS.md` with the human's taste (interviewed, never assumed), `AGENTS.md ## Learned`, a team roster for this project's domain (`hive-scout` designs it and picks skills, human approves; `required.txt` is not negotiable), `teams/ROUTING.md`, gates green on `main`, and the mechanical gates for the domain (`enforcement.md` on code, `domains.md` otherwise) installed by the scaffold or stabilise ticket. Not there → stop.
1. **Orient**: read `AGENTS.md`, `CONTEXT.md`, relevant ADRs, and the taste docs `CONVENTIONS.md` names; their defaults go into every brief and spec now, never learned in a review round. Unfamiliar repo → `graphify` once, keep the summary, never pass it to workers. Then the information gate, every work order, before any spec: you must be able to write, without guessing, (a) the outcome the human will see, (b) how a human checks it is done, (c) what is out of scope, (d) the areas and teams it touches, (e) constraints on tools, data, budget, and dependencies, (f) zero open questions. Any blank → grill the human: `/grill-with-docs` when `CONTEXT.md` exists, `/grilling` on a blank repo; one question at a time until all six are filled, answers logged to the run log. Work bigger than one milestone or one session → `/wayfinder` first (its map is a tracker issue, never a file), then the gate per destination. Never fill a blank with an assumption. Unattended and a blank remains → park the work order, take the next. Already grilled (run log says so) → skip. An open question of fact → `/research` in a Sonnet subagent; its finding decides, your preference does not.
2. **Tickets**: `/to-spec`, then `/to-tickets`; every ticket becomes a tracker issue, every milestone a tracker milestone, nothing written to disk. Enforce: route each ticket by `teams/ROUTING.md` (deliverable type or path → owning team; no row → ask the human, then add the row via a ticket); owned paths inside that team's `Owns`; one owner per file per wave; hotspot files (routes, registries, config, shared scene or project files) in a ticket that runs first; tags `difficulty:standard|hard` and `profile:<team>`. Two teams in one ticket → two tickets with a contract between them. A ticket whose outcome rests on facts outside the repo gets `needs-research`: its worker runs `/research` first and cites sources in its report. Milestones per `review.md`, one user-visible result each.
3. **Contracts**: you decide, a worker types. Per ticket, write into the issue body the interface (code: exported signatures in a code block, `/codebase-design` vocabulary; otherwise the deliverable's shape per `domains.md`) and the check in one sentence: name, input, expected result. Can't write them → `/grilling` until you can. Create and push `hive/<run>` (`stack.md`). Then one contracts worker per team in the wave (`roles.md`; Opus if any ticket is `hard`), one after another, commits stubs and checks to `hive/<run>` and shows each check red twice: once on the missing work, once on a deliberately broken input. A check that cannot go red on broken input measures nothing; rewrite it. You do not open the files.
4. **Dispatch**: protect `hive/<run>` (`enforcement.md` §1) so nothing merges without green CI. Agent Teams, one worktree per ticket, one PR per ticket into `hive/<run>`. Per worktree, `node .claude/hooks/hive-worktree.js <wt> <owned paths…>` before the worker starts. Spawn `hive-<team>-worker` if the repo defines one, else `hive-worker` with the team named, and the Agent call's `model` (prompt text does not change it): `standard`→`sonnet`, `hard`→`opus`. Worker gets the issue number, contract pointers, owned paths, team, scratch key `<run>-<id>`; runs `/implement` or the team's procedure; retry cap 2; reports once. Arm the stall check now (`operations.md`); a check written only in prose never runs.
5. **Escalate** one rung, never restart, never by your own hand: (a) same worker, failing output pasted back, mechanical failures only; (b) diff + red output to a fresh Opus worker, not the ticket; (c) two Opus fails → the contract is wrong, back to step 3 as a fresh task. `NEEDS dependency` from any worker → OSV query (`enforcement.md` §8), result plus the request to the human; never add a dependency yourself.
6. **Verify**: `hive-<team>-verifier` or `hive-verifier` with the team named (Opus), fresh context, gets ticket + contract + diff + report. Reads CI, runs the team's checklist, checks the diff stays inside the ticket's owned paths and the team's `Owns`. Ticket touches auth, input, secrets, file or network I/O, money, or personal data → `hive-security-verifier` as a second verifier; both must say `MERGE`. Verdict `MERGE | BACK-TO-WORKER (numbered) | CONTRACT-WRONG` as a PR review comment. Follow-ups never become tickets: a blocker is `BACK-TO-WORKER`; anything else is one line on the milestone's debt issue (`tracker.md`). Back-to-worker goes direct, one round, then it is contract-wrong.
7. **Merge** PRs sequentially in dependency order into `hive/<run>` with `gh pr merge` (worktree removed first, per `stack.md`), full suite after each read as an exit code, close the issue, then `TaskStop` the worker and its verifier; an idle agent repeats its report and burns tokens. Then `node .claude/hooks/hive-scratch.js --sweep <run>-<id>` deletes their scratch (`operations.md`). Conflict → an Opus worker of the owning team runs `/resolving-merge-conflicts`; you never resolve one. Wave merged → `hive-qa-verifier` once on the branch; `WAVE-RED` failures become tickets, not fixes. Milestone complete → the same agent with `model: opus` and the word `milestone` (`enforcement.md` §7, §10 on code). Its blockers are `WAVE-RED` tickets; the gate does not open over them.
7½. **Human review**: milestone complete and `WAVE-GREEN` → read `review.md`. Spawn `hive-guide`; it opens the review issue with brief, evidence, and the milestone's open debt. Notify, point the human at `/hivemind-review` in a second terminal, then poll the issue for a verdict in a background shell. You never relay the review. `ACCEPT` → next milestone. `CHANGES` → tickets, step 3, same gate again; `CHANGES revision`, or changes that are all small tweaks → revision mode. Human away → the unattended warning from `review.md`, continue only on the literal `UNATTENDED`.
8. **Close**: last milestone accepted. `hive-qa-verifier` with `model: opus` and the word `close` (`enforcement.md` §10 on code); red → tickets. Every open debt line is fixed, re-scoped into a future run's issue, or dropped by the human; none stays silent. Lessons pass and upstream proposals (`lessons.md`). Open the PR from `hive/<run>` to `main` linking the milestones; the human merges. Delete the branch protection and `hive-evidence/<run>` after, then `node .claude/hooks/hive-scratch.js --sweep <run>`. Session ending with open work → `/handoff`. Report cost per merged ticket from `ccusage` (`enforcement.md` §5).
