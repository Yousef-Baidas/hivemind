# Gemini CLI (and Qwen Code) vs. Claude Code features used by hivemind

Researched 2026-09-29 from shallow clones of the source repos (read in /tmp/harness-research/gc and /tmp/harness-research/qc) plus the in-repo docs and GitHub release lists.

## Notes and porting-relevant details (Gemini CLI)

- Hook parity is good for the core enforcement loop: BeforeTool deny+reason, AfterTool additionalContext, BeforeAgent additionalContext, AfterAgent deny-to-retry, SessionStart additionalContext all match Claude semantics. Field names differ: `decision/reason` (top level) and `hookSpecificOutput.additionalContext`, not `permissionDecision`. Tool names differ (`run_shell_command`, `write_file`, `replace`, `read_file`, `grep_search`, `mcp_<srv>_<tool>`); the matcher is a regex, so old Claude names (Bash/Edit/Write) must be re-mapped.
- The hook framework has no session-model field and no `permission_mode`. A model-ladder cap ("the lead's model caps every spawn") cannot be enforced from hooks except through `BeforeModel` (`llm_request.model` readable and overridable via `hookSpecificOutput.llm_request`). BeforeModel is a real lever, and it fires for every request.
- Subagents: definition files are close to Claude's (md + frontmatter), but there is no spawn-time model, no background mode, no SubagentStop, no worktree param, and no recursion (subagents cannot spawn subagents). The lead cannot dispatch workers via subagents with per-ticket models. Workable alternative: the lead shells out `git worktree add` then `gemini -p ... --output-format stream-json --approval-mode yolo --skip-trust -m <model>` per worker (one process per ticket), reading `result` JSON. This loses shared session state and hooks-in-subagent uncertainty, but gives per-worker model, cwd, and exit code.
- Skills have a cheap match: same SKILL.md + `.agents/skills/` alias, activated through a tool with user consent (consent prompt may block headless runs; UNCONFIRMED how it behaves in `-p` mode).
- SessionStart `additionalContext` in non-interactive mode is prepended to the user prompt, so it works in headless runs.
- Hooks are configured in settings.json with a project-level `.gemini/settings.json`; that is gated by folder trust when enabled. Extension hooks live in `hooks/hooks.json`. Docs warn that project hooks are a supply-chain risk (docs/hooks/best-practices.md), and hooks get a fingerprint/trust prompt (not verified in detail; UNCONFIRMED).
- Stable vs main: v0.61.0 stable is the latest release; main is 0.63.0-nightly. Subagents are labelled preview/experimental, and worktrees experimental, in docs. Expect churn.

## Biggest gaps for a hook-enforced multi-agent orchestrator

Gemini CLI:
1. No subagent lifecycle and no per-spawn model: no SubagentStart/SubagentStop hooks, spawn tool takes only `agent_name` + `prompt` (model fixed in the agent file), no background mode, no worktree isolation for subagents. Model-ladder caps and "verifier must finish" gates cannot be enforced per spawn. Use one process per worker instead.
2. Hooks lack model/permission-mode in the base input, and it is UNCONFIRMED whether they fire inside subagents; there is no scriptable status line (only fixed footer item ids) and no commit co-author trailer setting.
3. Google-only models (no OpenAI-compatible or Ollama backend), and features are preview/nightly-heavy (stable v0.61.0 vs main 0.63.0-nightly).

Qwen Code closes most of these (Claude-style hooks including SubagentStop/Stop-block, `isolation:"worktree"`, scriptable status line, gitCoAuthor, OpenAI-compatible providers); its remaining gap is that a per-call model choice on spawn is not documented.
